## Compose advanced graphics effects with SwiftUI (id: wwdc2026_322, 17.9 min)

Basis: transcript and 13 of 13 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/322/.

Central thesis: advanced graphic effects in SwiftUI are born from composing simple APIs into a kind of pipeline (data that comes in, transforms, and passes along), not from writing complex, isolated code. In the speech, the presenter sums it up: the advanced lies in the construction, not the complexity.

The design process Apple describes: start from an already existing interface (in this case, a fairly simple podcast transcript screen) and identify which data is already available (episode cover, playback state, transcript text). The question is not "what data do I need," but "how do I transform the data I already have." Each visual element becomes a "pipe" (a transformation), and pipes can be connected, branched or merged. The presenter builds the effect in visible steps: blur the cover, apply a shader, animate over time, sync the transcript with time, and finally position a floating timestamp with custom alignment.

Principles stated: the progressive disclosure of SwiftUI's APIs lets each "pipe" work on its own before being combined; the creativity is in how the pieces connect, not in the amount of code.

Concrete interface-building techniques:
- Blur modifier to soften the background image before applying effects on top of it.
- Three types of shader effect in SwiftUI: colorEffect (transforms each pixel's color based on its original position and color, useful for simple effects like black and white), distortionEffect (resamples from another position in the original image, useful for geometric effects like shearing) and layerEffect (the most flexible, gives access to the entire layer of the view, useful for effects like blur that depend on multiple neighboring pixels).
- Use of NoiseTexture: a precomputed image of smooth random values, whose red and green channels carry different noise patterns; used as an organic offset in X and Y per pixel, sampled via UV and a sampler in repeat mode.
- Domain warping: sampling the noise twice (the second sampling offset by the first) to get organic, fluid patterns, instead of a uniform displacement.
- TimelineView with an animation schedule to drive shaders over time, since shaders are stateless (with no memory of the previous frame); the timestamp of each frame is passed to the shader.
- Syncing the transcript with playback time: highlighting the current line, using onChange to scroll to the current line, a timestamp overlay present only on the active line.
- Custom alignment guides for floating view attachment: every view has an alignment point (like a "pin" that runs through two views at the corresponding point); it is possible to override that point semantically (for example, making a subview's "bottom" point correspond to its top edge) to position an element pinned to a container's edge without manually calculating offsets.

Examples cited: Apple Music's "live lyrics view" was the stated inspiration for the animated cover effect with synced transcript; the presenter's own podcast app is the example built throughout the session, including a vector icon rasterized by the GPU used to explain what a shader is.

Quotes:
"The 'advanced' lies in the construction, not the complexity."
"Each pixel executes independently, with no awareness of its neighbors."

## Design no-code games with Reality Composer Pro 3 (id: wwdc2026_252, 18.9 min)

Basis: transcript and 17 of 17 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/252/.

Central thesis: Reality Composer Pro 3's Script Graph makes it possible to build 3D games in RealityKit through event-driven logic, without writing code, with fast iteration tested directly on visionOS.

The design process Apple describes: the idea is born from a "wish" (a desire for something to exist) and the presenter works until it exists. The build follows layers of increasing complexity: first the simplest logic (dragging an object), then refining the feel (drag speed, adjusted by testing live on Vision Pro), then physics (force, gravity, friction), then organization (subgraphs), then communication between entities via custom events, and finally integration with SwiftUI. At each step, the author tests in the Reality Composer Pro viewport and, when possible, on the real device, adjusting parameters published in the Inspector.

Principles stated: fast testing and iteration are central to any creative workflow, and testing the real feel of an interaction requires trying it on the device, not just on the Mac screen. Organizing the logic (cleaning up and naming blocks) is treated as part of the creative process, not as a separate task.

The design process in Script Graph, step by step:
- Input components: Input Target Component (makes the entity a gaze target), Collision Component (defines the target size), Hover Effect Component (highlight on look).
- Event nodes (On Drag) triggering Set nodes (such as Set Transform) that write to components.
- Public input variables (such as dragSpeed, type number, default 1.3) editable in the Scripting Component's Inspector; when edited per instance, the value becomes an "Override", unique per component, allowing multiple instances with the same Script Graph but different behaviors.
- Physics: Physics Body Component; Add Force node (additive force, requiring calculating the change in drag position frame by frame, stored in variables such as targetPosition and dragDelta); Set PhysicsBodyComponent to dynamically turn off gravity while the object is dragged and increase the linear damping (more friction, less "jitteriness").
- Prototyped Subgraphs: select a set of nodes, "Compose Subgraph" to clean up the reading of the logic, and "Convert to Prototyped Subgraph" to reuse that block in any Script Graph in the project via a Custom Node Library.
- Custom events (Custom Event, with properties such as nutPosition) let the Script Graph of one entity (the nut) send data to the Script Graph of another (the squirrel), triggering rotation and a material swap (Set Material Parameter, type Bool) to change texture.
- Send Scene Event connects the Script Graph to Swift code: a scene event (squirrelTalk, with variable sayThis) is listened for in Xcode and used to show a SwiftUI attachment (a "speech bubble") over the entity.

Examples cited: the very game built in the session, about a squirrel sleeping on a nut that the player drags home; the speech mentions that the complete Squirrel Sample Project is available on Apple's developer site, including additional mechanics such as walking, jumping and a visionOS ornament for level navigation.

Quotes: there is no especially notable short, isolated quote beyond descriptive observations of process; no quote included so as not to force a passage out of context.

## Create UI prototypes using agents in Xcode (id: wwdc2026_227, 18.2 min)

Basis: transcript and 16 of 16 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/227/.

Central thesis: coding agents in Xcode are useful collaborators for exploring design possibilities quickly, but the final judgment about the best experience remains the designer's, never the agent's.

The design process Apple describes, in three phases: first, explore UI possibilities by generating multiple variations from specific (not vague) prompts; second, bring in real content and edge cases so the app feels "lived-in"; third, adjust (tune) key moments of animation and interaction using tuning panels built by the agent itself.

Principles stated: vague prompts lead to arbitrary results and lock the designer into a bad starting point (anchoring), including generating "feature creep" when the app is forced to fit into a navigation decided too early; effective prompts define the desired features, give style cues and always ask for multiple options, each with its own named Swift preview; the presenter's text sums up the method as "go wide, remix, repeat".

Concrete interface-building techniques:
- Two base Xcode features used: coding agents (conversations that generate real code from a natural-language description) and Xcode Previews (instant preview without a rebuild).
- When asking for multiple variations, each one should have its own name and preview, which allows switching between them quickly.
- After choosing favorite elements among variations, the next prompt should list exactly which elements to remix.
- When bringing in real content: ask for multiple previews of edge cases thought through beforehand by the designer (for example, when there is no meeting scheduled, very long texts that can truncate or break into multiple lines, a number of members growing without limit); ask for the example content to stay isolated in its own file, reusable and editable.
- Two animation styles described: ease (smooth acceleration and/or deceleration, with configurable duration) and spring (imitates the movement of an object drawn by a spring, with three adjustable parameters: stiffness, damping and mass).
- Other dynamic interface elements cited: friction and inertia (perceived weight when dragging something), device motion (response to accelerometer/gyroscope) and haptics.
- Building a tuning panel: ask the agent to break the animation into named phases (sharing vocabulary between designer and agent); ask for a side-by-side layout in a wider window to avoid context switching between panel and UI; controls isolated by phase allow adjusting delays and staggered entry times until reaching the desired result.

Examples cited: a book club app built live, with ten variations generated from a detailed prompt (named, among others, Club Hub, Cozy, Editorial and Blueprint Atelier, plus a variation with a "racetrack" metaphor for tracking progress); the Music app, used as a reference for perceived weight when closing a sheet; Apple Cash in Wallet, as an example of iridescent parallax responding to device motion; Find My, as an example of using haptics to communicate proximity to an object being located.

Quotes:
"Do not delegate critical thinking to these tools."
"Go wide, remix, repeat."

## Rediscover the HTML select element (id: wwdc2026_315, 9.5 min)

Basis: transcript and 7 of 7 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/315/.

Central thesis: the native HTML select element can now be completely customized with CSS (customizable select), preserving the built-in semantics and accessibility, without needing to resort to heavy JavaScript libraries or div stacking.

The design process Apple describes: applied to a fictional photography portfolio site, the developer starts from the native select (which already offers keyboard navigation and VoiceOver reading out of the box), and customizes it layer by layer: first the visible select button, then the dropdown menu itself, then the content of the options (going beyond plain text), and finally the select's own button replaced by rich content. At each step, the author checks how the result behaves in browsers without support for the feature, confirming that the experience remains usable (progressive enhancement).

Principles stated: reusing the semantic select element keeps accessibility without extra effort; full visual customization should not require giving up native semantics; testing with unsupported browsers and with assistive tools is part of the process, not an optional step.

Concrete interface-building techniques:
- appearance: base-select on the select element to get a reduced set of customizable styles while keeping the font-family inheritance from the body.
- The ::picker-icon selector to customize the select's arrow (the content property to change the glyph, width to size it) and use of the :open pseudo-class to apply different colors when the menu is open.
- To style the dropdown menu: ::picker(select) on the select element with appearance: base-select to move away from the menu's native style; ::checkmark on the option element to customize the check icon of the selected option; typographic emphasis (bold) on the marked option and dimming of the others.
- Rich content inside the options: any content (images, videos, emojis) can be placed inside an option, including SVG with alternative text (empty alt when the text label next to it already covers the information, so as not to duplicate reading in screen readers).
- Grid layout for the menu: grid-template defines rows and columns, gap defines the spacing between cells, reusing the CSS Grid syntax that already exists inside the dropdown.
- Replacing the select's default button with a button element as the first child, allowing rich content (text label and/or image) inside the button itself; the element called "selectedcontent" in the text automatically shows the rich content of the selected option inside that customized button.

Availability cited: feature coming to Safari 27 and already available in Chrome 135; possible to test today via Safari Technology Preview or Safari Beta.

Examples cited: a sorting select (Sort by) styled to match the site's visual identity; a photo category select with SVG icons inside each option, reorganized into a grid to fit the window; a radial color picker mentioned as built entirely with customizable select; joint use with CSS Grid Lanes (referring to another session from the same group) for the site's image layout.

## Design intuitive search experiences (id: wwdc2026_292, 16.3 min)

Basis: transcript and 14 of 14 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/292/.

Central thesis: good search design depends on where the search field is placed in the app, because the position communicates the search's scope (what exactly will be searched) and affects usage ergonomics, especially with the new patterns brought by Liquid Glass.

The design process Apple describes: it starts with the standard elements of the Search Field (magnifying glass icon, placeholder, clear button, Cancel button on iOS when focused), then moves to choosing a placement pattern by answering two central questions: how do people navigate the app (is there a tab bar?) and what is the search's scope (the whole app, a section, a library?). Finally, it covers best practices for suggestions, filtering and empty states.

Principles stated: the search field's position should clearly reflect what will be searched, so as not to create the wrong expectation about scope; searches should prioritize showing relevant results as soon as possible, so that, when ranking works well, the person doesn't need to type the whole query; filters should be shown only when relevant and contextual, so as not to overwhelm the person searching.

Concrete interface-building techniques:
- On iOS: search can live in the toolbar (as a field or button), as a tab, or as a field below the top toolbar/in the content area. When in the bottom toolbar, the field animates above the keyboard, optimizing reach and typing; when inline, it stays at the top even when active, avoiding UI at the bottom.
- Search Tab pattern in apps with tabs: it can be a standard tab (leads to a landing page with the field at the top, leaving room for content suggestions before searching) or a "prominent" tab with a button appearance (engages the search and the keyboard immediately on tap).
- On iPad and Mac: search can sit in the trailing position of the top toolbar, at the top of the sidebar, or at the top of a dedicated search tab/section; in toolbars with multiple items and groups, the search field scales or collapses into a button depending on available space, moving excess items into a menu.
- Scope bar as a lightweight filtering control (toggling between searching all mailboxes or just the current one, for example).
- Search tokens: they filter by specific keywords that appear while the person types, appear highlighted inside the field itself and can be combined to create custom filters in more natural language; because they are less discoverable, tokens should not replace more visible filter controls, working best combined with a scope bar or other filters.
- Suggestions: recent searches shown inline when the field gains focus on iOS, in a menu when the field is in the toolbar/sidebar on iPad and Mac, or alongside other content suggestions in a Search Tab; it's recommended to be selective about which recent searches to show and always allow removing them (swipe gesture on an individual item, button to clear everything).
- Empty state: use a content unavailable view configured for search (search symbol, title, subtitle) and show the searched text in this state, to help identify typos, instead of leaving a blank screen.

Examples cited: Mail (search in the bottom toolbar, more ergonomic and adjacent to other primary actions, with field width that adapts to the number of neighboring items); Stocks (search in the top toolbar because the bottom of the list is occupied by a sheet); Apple TV (standard Search Tab, showing genres and categories before searching, for exploratory context); Phone (prominent Search Tab, going straight to the keyboard, for those who already know what they're looking for); Apple Music (inline search in the library, with a specific placeholder reinforcing the scope); Notes and Files (search in the toolbar's trailing position, a common and familiar pattern); Freeform (search in the toolbar directly filtering the frames displayed in the detail area); Settings (search in the sidebar, filtering navigation); Maps (contextual filters by place type, from restaurants to trails); Photos (combinable tokens, such as photos from a specific place in a specific year).

## Craft clear names for features and labels in your app (id: wwdc2026_290, 15.1 min)

Basis: transcript and 11 of 11 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/290/.

Central thesis: naming features, labels and products is a design decision as fundamental as layout or interaction, and there is a concrete method (criteria and an audience exercise) for arriving at better names, not just more creative ones.

The design process Apple describes: first, evaluate any candidate name against three criteria (belongs, expectations, works everywhere), treated as a guide and not as a rigid rule that must always be fully satisfied. Then, a name discovery exercise starting from the audience: identify who the audience is, and then, with that audience in mind, write loose ideas (without filtering) in three categories, what the person should think, feel and do upon encountering the feature; group the ideas by recurring theme; from the themes, generate name candidates; discard the ones that do not pass the criteria; test the survivors by saying them out loud in a natural sentence like "hey, look at the [name]" to check whether they sound natural.

Principles stated, with the why of each:
- Belongs (to belong): a name that truly belongs works on every level, including matching what has already been named around it; the why is to avoid a name that sounds right in isolation but clashes with the rest of the app.
- Expectations: when someone reads a name, they are already predicting what they will find; the why is that delivering exactly that builds trust, and failing at that breaks trust, especially in financial contexts.
- Works everywhere: a name needs to hold up across different languages, markets and contexts; the why is to avoid rework and confusion when localizing.
- When naming, thinking about the function or technology behind it is natural for whoever builds it, but whoever uses the app wants to know what that does for them; that is why the starting point of the exercise is always the audience, not the implementation.

Concrete techniques: use of a "gut check" (saying the name out loud in an everyday sentence) as a practical test of naturalness; distinction between descriptive, emotional and "branded" names (invented from recognizable parts) as equally valid paths, whose choice depends on which criterion matters most in that specific context.

Examples cited: in Apple Cash, the label for the available balance was tested as "Spending Power" (sounds appealing but ambiguous, and can sound like judgment when the amount is low or zero, breaking the trust a payment service requires) and as "Current Funds" (descriptive, but sounds like spreadsheet language, not like something said in natural conversation); the name chosen was "Balance", a standard industry term, clear and neutral. In a hypothetical gym app, the example contrasts "Basic Access"/"All Access" (clear) with "Lightweight"/"Heavyweight" (more aligned with the brand, but with a learning curve, requiring more work to explain). In Apple Maps, the audience exercise led to the themes ease, excitement and security for the visited places feature, resulting in the name "Visited Places" (descriptive, already coexists with the word "places" used throughout the interface, communicates that the places belong to the person and are not read by Apple, and translates well). In Photos, the feature that algorithmically groups photos by moments was named "Memories", an emotional name rather than a technical one, because whoever opens the feature is looking for a memory, not thinking about algorithms. In Apple Podcasts, the process of naming the feature that isolates voices and reduces background noise went through "Isolate Vocals" (a technical audio engineering term), "Clarify Speech" (tells only half the story) and "Enhance Playback" (vague about what and for whom), arriving at "Enhance Dialogue" (answers both questions and is already used in a similar feature on Apple TV, reinforcing that it belongs). In Apple Music, "AutoMix" is cited as an example of a "branded" name: an invented word, but one that self-explains through the sum of its parts (Auto from automatic, Mix from mixing).

Quotes:
"Every good name you choose makes the next one easier."
"That person isn't thinking about algorithms. They're looking for a memory."

## Learn CSS Grid Lanes (id: wwdc2026_314, 10.4 min)

Basis: transcript and 8 of 8 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/314/.

Central thesis: CSS Grid Lanes is a new layout mode (the pattern popularly known as masonry) that sits between Flexbox and Grid, allowing items of different sizes and proportions to distribute themselves across multiple columns or rows while preserving their natural proportions, without requiring JavaScript.

The design process Apple describes: the presenter frames any layout mode as an answer to two questions (where the items go, how much space they get) and uses this to position Grid Lanes among the already known modes: Flexbox structures a single axis (a lane of items that just keep flowing in the same direction when wrapping); Grid structures two fixed dimensions (columns and rows), which creates empty spaces when items have different proportions; Grid Lanes structures only one dimension and leaves the other free, distributing content across multiple lanes instead of just one, and each new item is placed in the column (or row) that ends up shortest.

Principles stated: forcing images of different proportions into a traditional Grid leaves only three bad options, stretch (distorts), enlarge (breaks out of the container's limits) or crop (loses information); Grid Lanes avoids this dilemma by structuring only one dimension; the layout should adapt to the content, not the other way around.

Concrete interface-building techniques:
- display: grid-lanes as a new display type; grid-template-columns defines the number of tracks and the width of each one, using the fr unit (fractional unit, which divides the container's available space into fractions); gap defines the spacing between items, the same as in CSS Grid.
- To reverse the direction (from vertical "waterfall" to horizontal "brick wall"), just swap grid-template-columns for grid-template-rows; only one direction can be chosen at a time, never both.
- Columns of different widths are possible (for example, a center column with twice the space of the side ones); auto-fill combined with minmax(200px, ...) lets the browser decide how many columns fit, each with a minimum of 200 pixels, able to grow to fill the space; it is also possible to create a repeating pattern of narrow and wide columns.
- grid-column: span 2 stretches an item across two columns, reorganizing the rest of the layout around it; it is also possible to position an item explicitly by column (start/span), but the row it falls into is still decided automatically by Grid Lanes, never manually.
- subgrid: with display: grid-lanes and grid-template-columns: subgrid on an item, that item's inner content (for example, the image and text of a card) starts participating in the parent container's layout as items of its own, each sized to its own content; Grid Lanes can be nested with regular Grid in either direction.
- flow-tolerance: by default, the browser places each new item in the shortest column; flow-tolerance (default of 1em) loosens this rule by asking, for each new item, whether the difference between the tallest column and the shortest one is smaller than the tolerance, and in that case fills the tallest column anyway, instead of alternating sides with every item; this avoids a zigzag visual reading that would mismatch tab order (accessibility) from visual order.
- Web Inspector with full support for Grid Lanes: the overlay shows column and row lines, order numbers over each item, and the spaces (gaps) between them, useful for debugging unexpected flow-tolerance results.

Examples cited: a photography portfolio layout with images of varying proportions (the same scenario as the video about customizable select from the same group); a recipe card that spans two columns via span, with its internal image and text organized via subgrid.

Availability cited: Grid Lanes available since Safari 26.4, and behind an experimental flag in other browsers.

## What's new in SwiftUI (id: wwdc2026_269, 28.3 min)

Basis: transcript and 20 of 20 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/269/.

Central thesis: the new features in SwiftUI in the 2027 releases cover visuals (refined Liquid Glass), resizing, adaptive toolbars, an expanded document API, presentation and interaction improvements, and gains in performance and data flow, all demonstrated using a sample app for creating sticker pages.

The design process Apple describes in this session is essentially an API tour, organized into four blocks: appearance (Liquid Glass and resizing), documents (reading/writing to disk), presentation/interaction, and performance/data flow. Each block is demonstrated by adding a new capability to the same sample app.

Principles stated: apps get the refined Liquid Glass visual automatically, without changing code, but there are still fine-tuning points for those who want to go beyond the default; typing/compilation performance (type-checking) is also treated as part of the experience of those who develop, not just those who use the final app.

Concrete techniques for building interface and API:
- Liquid Glass: custom elements can be marked as "interactive" to respond more fluidly to clicks (also optimized for mouse pointer on Mac); appearsActive (environment value) lets you reduce the opacity of custom elements when the window loses focus, replicating native behavior; iPad and Mac menu bars now show a minimal set of icons by default, reserved for key actions, and the labelStyle(.titleAndIcon) modifier lets you highlight a specific item with icon and title.
- Resizability: iPhone apps become resizable in iOS 27; in Xcode 27, Live Previews gain resize handles to interactively test behavior across different window sizes, including scenarios like iPhone Mirroring or running as an iPhone app on iPad.
- prominent tab role: makes a specific tab visually stand out (in the example, a shopping cart positioned on the trailing bottom edge, different from the other content tabs).
- Toolbar: visibilityPriority(.high) forces items (like Undo/Redo) to stay visible when space shrinks; the new ToolbarOverflowMenu container groups less-used actions directly into the overflow menu; the topBarPinnedTrailing placement ensures an item (like the Share button) is never hidden; toolbarMinimizeBehavior(.onScrollDown) in the navigationBar placement makes the navigation bar automatically get out of the way when scrolling down, freeing up screen space.
- Document API (SwiftUI): DocumentCreationSource declares multiple document creation origins (for example, blank or from a photo), each associated with a NewDocumentButton; the chosen origin reaches the document's initializer via the context parameter. DocumentGroup as the app's first Scene declares the document architecture; the document class uses the Observable macro, so views only update when a property they depend on changes. For writing, the document conforms to WritableDocument: a list of supported formats, a snapshot method that returns the current content (an immutable struct representing the document at an instant), and a Writer conforming to DocumentWriter, whose write method is nonisolated and asynchronous (allowing background disk operations without blocking the UI); it's possible to compare the current snapshot with the previous one to write only what changed, and report progress via Foundation's Subprogress API. For reading, the symmetric pair is ReadableDocument/DocumentReader. The same write infrastructure was extended to export additional formats (like PNG via Core Graphics), just by adding the new content type to the supported list and handling the case in the write method.
- Reorderable API: the Reorderable modifier on ForEach combined with reorderContainer on the container (List or LazyVGrid, with the same code serving both) enables drag to reorder, using the open source swift-collections package to apply order changes; this capability now also comes to watchOS for the first time.
- Swipe actions are no longer exclusive to List: the swipeActionsContainer modifier coordinates swipe actions in any scroll container, like a LazyVStack.
- confirmationDialog and alert now support the same item-binding pattern that sheet already used, simplifying the display conditioned on an optional value (in the example, a sticker to be deleted).
- AsyncImage now automatically supports standard HTTP caching, respecting the server's cache headers, with no code change; for fine control, it's possible to build your own URLRequest (for example, to set a cache policy) or a custom URLSession/URLCache, associated via the asyncImageURLSession modifier.
- Instances of Observable classes stored in State properties are now initialized lazily (from the conversion of State from Dynamic Property to macro): the instance is only actually created on the view's first initialization, even if the view is reinitialized afterward; this behavior was backported down to iOS 17 and macOS 14. This can produce a "use before initialization" error in code that assigns a default value and also assigns a value in init, whose fix is to remove the unnecessary default assignment.
- ContentBuilder: a single unified builder behind Section, Group, ForEach and others, eliminating the combinatorial explosion of overloads the compiler needed to test to type-check deeply nested views, which used to be able to produce the error "the compiler is unable to type-check this expression in reasonable time"; it works on any deployment target, since it's an evolution of the existing ViewBuilder.
- New agent skills included in Xcode 27, accessible through the Coding Assistant: SwiftUI Specialist Skill (SwiftUI best practices) and What's New In SwiftUI Skill (adoption guide for the new APIs in the 2027 releases); exportable for use outside Xcode with the "xcrun agent skills export" command, generating Markdown files.

Example cited throughout the session: an app for creating sticker pages (photos with stickers of a dog named Pretzel and a cat named Kishka), including a sticker pack store (with a "WWDC26" pack) used to demonstrate AsyncImage caching.

## Design immersive environments for visionOS apps and the spatial web (id: wwdc2026_234, 16.0 min)

Basis: transcript and 16 of 16 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/234/.

Central thesis: visionOS photorealistic immersive environments (such as natural landscapes in real depth, with parallax) are built in three disciplined phases, pre-production, production and post-production, combining high-fidelity photography, technical reference and deliberately economical motion and sound effects to fit the real-time rendering budget.

The design process Apple describes:

Pre-production: the team starts by asking why it is building that specific environment, what qualities it should convey and how it will be used; concrete use cases shape composition decisions (for example, the media environment was sculpted around a large screen and an ideal viewing "center line"; the Keynote environment was designed for public speaking practice, with sound deliberately absent to keep focus and light concentrated on the stage, as it would be in a real presentation). When the environment reproduces a real place, the team visits the location in advance (scouting) to decide the person's main point of view and what will be visible if they turn around; in visionOS, the person sees approximately 81 degrees of the scene when fully immersed. Scouting also serves to identify elements that should not appear in the final version (a road and dense vegetation were flagged and later removed in the Mount Hood case). When the location is not physically accessible (as with the Moon environment, based on photography from the Apollo missions) or when the team wants to better understand a terrestrial location (as with the Yosemite lighting study, made from digital elevation models combined with Earth's orbit, to determine exact capture days and times), reference material is essential. Before moving on to production, it is recommended to visualize the environment in layers (from background to foreground), identify which elements will need motion and what spatial audio to attach to them. Pre-production is also where welcome changes of direction emerge: a scale model of the solar system, built to understand how the Sun would light Jupiter's moons, led the team to decide that the environment needed to allow the passage of time, which became a central requirement of the final design.

Production: capturing high-quality photography directly at the source makes all the following work easier. In the Yosemite case, the team returned to the exact point identified during scouting with a detailed capture schedule, since season, weather and time of day drastically change the result (light changes quickly near sunrise and sunset); the recommendation is to set aside more time on location and capture more photography than seems necessary. Technical capture best practices cited: a tripod leveled at 1 meter off the ground with wide depth of field; when possible, a second camera at 2 meters of height firing simultaneously, useful in post-production to fill in parts of the scene not visible from the main point of view; using a rig and lens that cover the entire scene at 360 degrees to produce a stitched panorama; bracketed exposures to capture the wide dynamic range between sun and shadow; knowing the target display and capturing more resolution than seems necessary, given that, for visionOS, an environment reads sharp at 40 pixels per degree, which makes a 360 degree panorama of 14,400 by 7,200 pixels an ideal target. Secondary reference and measurement photography is also recommended: point clouds produced by photogrammetry and LiDAR can become meshes and reveal, for example, that terrain that appears flat actually has a slope, which changes 3D asset construction decisions; Macbeth charts and chrome and gray spheres photographed alongside the main photography help computer-generated elements integrate convincingly; video of moving elements serves as an indispensable reference for building believable motion shaders, along with a record of what sounds, if any, are associated with that motion. When it is not possible to photograph a real panorama, the alternative is to create a rendered panorama, which gives full control over the scene at any point in time.

Post-production: the first step is cleaning up the panorama, removing the camera rig itself, footprints and people, plus elements already identified as unwanted in pre-production (in the Thorsmork case, mid-ground vegetation considered visually "cluttered" and shrubs that were too dominant in the framing were refined through successive iterations of digital matte painting and rendering of computer-generated assets, with constant attention to color balance and lighting consistency). The refined panorama is then mapped onto a 3D mesh in UV space; parts of the scene not visible in the main panorama are filled in with the secondary photography and with computer-generated renders. Verification techniques cited: constant A/B comparison between the 3D asset and the original panorama to ensure texture transfer keeps its quality; checking consistent sharpness between nearby elements, to convey correct scale; "flopping" (mirroring) the entire scene to see it with fresh eyes when visual familiarity tires the judgment; subjecting the environment to extreme gamma and gain values to reveal color and value inconsistencies, including data loss during texture transfer, which can become more evident on different displays. Finally, sound and motion complete the sense of immersion: spatial audio sources are positioned next to specific elements of the scene (for example, an emitter with the sound of running water placed where the river winds around large rocks in Thorsmork); for motion, custom shaders balance visual fidelity and power efficiency.

Concrete efficient motion techniques, detailed with the Bora Bora example: UV flow maps give clouds a continuous sense of evolution and direction at low cost, and weighting flow speed in different parts of the sky helps convey scale and depth; cloud shadows on the terrain are not rendered lights, but a rolling mask that darkens the terrain textures, with direction and speed combined with the clouds above so they appear connected even without being physically calculated; denser, more defined shadows under the palm trees are pre-rendered into "flip book" style textures that darken the terrain textures, trading the cost of rendering soft shadows in real time for a convincing precomputed approximation; palm fronds use meshes of fairly reduced complexity, with wind motion coming from a UV flow map, while trunks and fronds sway more smoothly than the individual leaflets thanks to hierarchical vertex animation and layered sine waves (stacking low and high frequencies to get variation that never repeats); the water has hue, saturation and brightness modulated over time to simulate subsurface scattering of sunlight, and its waves move through layers of normal maps and rolling textures.

Principles stated: be intentional with everything you add or remove, being able to justify each choice; build a composition in which every element of the scene feels like it belongs where it lives; tie every aspect of the scene together with sound and motion; and, as a final reflection, that the best way to know whether a design is working is to try to break it, without excessive attachment to any single idea.

Examples cited: the system environments Mount Hood, Moon, Jupiter, Yosemite, Thorsmork and Bora Bora, plus the Keynote environment mentioned separately to give context for how intended use changes sound and light decisions.

Quotes:
"Often the best way to know your designs are working, is to try to break them."
"Be intentional with everything you do."

## Dive into lazy stacks and scrolling with SwiftUI (id: wwdc2026_321, 21.2 min)

Basis: transcript and 15 of 15 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/321/.

Central thesis: LazyVStack and LazyHStack only evaluate and render the views that are actually visible, estimating heights, widths and scroll position for everything off screen; understanding this internal mechanism is what avoids everyday performance and scroll-behavior pitfalls.

The design process Apple describes in this session is, essentially, an explanation of an internal mechanism followed by recommended patterns and patterns to avoid, built on an example app of origami instructions.

Principles stated: the efficiency of a lazy stack comes exactly from not loading everything at once, but this has a precision cost, the size of off-screen views is estimated, not measured; code that assumes precision where there is only estimation (absolute offset, conditional view count) tends to behave unstably.

Mechanism and concrete interface-building techniques:
- A LazyVStack positions views from top to bottom and stops loading as soon as the visible rectangle is filled; as you scroll, it adds views as needed and removes the ones that leave the screen.
- The height of off-screen subviews is estimated from the average height of the views already positioned and the estimated number of remaining subviews; the ideal width of the stack is that of the first subview (which is why, in the example app, an infinitely flexible first view makes the stack occupy the width of the screen).
- The total estimated height can change during scrolling, as the stack learns more about the layout of newly loaded views; the same applies to the estimated space above the visible region, which affects the scroll view's content offset (example cited: after a screen rotation on iPhone, the stack keeps the view visible at the top anchored, and only corrects the space estimate above when scrolling back to the top, adjusting the content offset so that it is exactly zero at the top).
- A LazyHStack nested inside a LazyVStack (for example, a horizontal photo showcase inside the main list of steps) has an ideal height equal to that of the first subview; if the content of each item varies in height (such as a caption with a variable number of lines), the recommendation is to fix the height (for example, with a line limit and reserved space), since the stack cannot know in advance the largest caption among all the items not yet loaded.
- pinnedViews on LazyVStack allows pinning the header of a Section (for example, the title of the photo showcase) while scrolling.
- Pattern to avoid: applying a .scrollTransition that pushes a view outside its original frame makes the lazy stack, which only considers the original position, wrongly conclude that the view has already left the screen, making it disappear too soon; the recommended alternative is to use an effect that does not shift the frame, such as scale effect.
- Pattern to avoid: basing UI visibility (such as a "scroll to showcase" button) on the scroll view's absolute content offset, which is estimated and unstable; the recommended alternative is to use the relative positions of subviews within the visible region, such as the .onScrollTargetVisibilityChange modifier (in the example, with an 80% visibility threshold).
- Correspondence between view structs and subviews loaded by the stack: a ForEach normally resolves to one subview per item; but when the body of a view (such as StepView) contains, at the top level, two views without a wrapper (such as a VStack) around them, the LazyVStack loads those two views as separate subviews; when a view resolves to a dynamic number of subviews (for example, zero or one, depending on an environment value such as detailLevel), the lazy stack, which addresses visible subviews by index, needs to keep previous views alive longer than expected just to know whether the indices would change, which causes unnecessary reevaluations even off screen when another, unrelated environment value changes. Recommendation: filter at the data level (for example, with a Predicate in a SwiftData Query) instead of conditionally hiding inside the view's body; unwrapping an optional in the view's body has the same side effect and should be avoided the same way, preferring to show an alternative state (such as a ContentUnavailableView) higher up in the hierarchy.
- Prefetching: while scrolling, the lazy stack anticipates part of the work of displaying a view (evaluating body and layout) even before it enters the screen, spreading that cost across multiple frames to avoid frame drops (hitches) perceptible as stutters; because of this, a view's body can be evaluated during prefetch without onAppear ever being called, if the scroll direction reverses before the view actually appears. Because of this, loading everything in onAppear is not a good idea, since the work done in prefetch is discarded and needs to be redone; the recommendation is to configure the view already in the initializer, leaving it in a reasonable state before it appears, and, when loading is not essential but is useful to get ahead of (such as fetching a diagram from the internet), start that loading from an observable object (such as a DiagramLoader tied to a cache) already in init, to benefit from prefetch.
- Views that leave the screen are not removed from memory immediately; the stack keeps them for a number of updates, in case they become visible again; when they are finally removed, associated state variables are erased along with them, so data that needs to survive scrolling (such as a highlight state) should not depend on local @State, but on model objects or bindings coming from outside.
- Programmatic scrolling works even for off-screen views, estimating the target position and updating that estimate on every frame during an animation; it is more performant when each ForEach item resolves to exactly one subview, allowing the stack to consult the ForEach to find the destination ID without building any view, and when the stack can quickly count the subviews near the destination. Another pattern to avoid is changing a view's layout after it has already appeared (for example, using onGeometryChange to update a state that triggers another layout pass), which hurts scroll smoothness by pushing content after the original height has already been measured; the recommendation in this case is to use a custom layout.
- Use of onAppear for legitimate cases such as infinite scroll: a ProgressView at the end of the list, with onAppear triggering the fetch of the next page of content.

Example cited: an origami instructions app (steps to fold a swan), with a photo showcase in a nested LazyHStack, a shortcut button to scroll to that showcase, and a StepView whose internal structure (diagram and instructions) is used throughout the session to illustrate the different ways view structs correspond to loaded subviews.

## Principles of great design (id: wwdc2026_250, 17.3 min)

Basis: transcript and 15 of 15 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/250/.

Central thesis: for Apple, design is making something with intention, focusing on what matters most to people; the session defines nine fundamental principles (purpose, agency, forgiveness, responsibility, familiarity, flexibility, simplicity, craft and delight) to guide design decisions on any Apple platform, making explicit that there is no fixed formula for combining them.

The design process Apple describes: before sketching any screen or writing any line of code, ask whether what is being built has purpose, since every feature asks for time, attention and trust from whoever uses it, resources that cannot be wasted; choosing what to build is, in practice, deciding what not to include. The session does not describe a linear process of steps, but a set of questions and lenses to apply during design, acknowledging that reinforcing one principle can seem, at first glance, to compromise another.

Principles stated and the why of each:
- Purpose: each feature consumes people's time, attention and trust; that is why deciding what to build is, in practice, deciding what to leave out.
- Agency: putting people in control, offering choices instead of a predetermined path; an interface should never get in the way of what someone is trying to do, and people engage more when they control their own experience at their own pace.
- Forgiveness: giving agency also means that people will make mistakes; that is why undoing any action should be made easy, and when something is destructive, confirm before acting; interruptions should be used carefully, only when someone is about to make a big mistake, because forgiveness sustains agency by giving the confidence that it is always possible to recover.
- Responsibility: acting in people's best interest, starting with privacy, treated as a human right; responsible interfaces ask for personal data at the right moment, only what is necessary, and are transparent about what it is for, instead of asking for permissions as soon as the app opens, before the person even understands what the app does. Responsibility also means keeping people safe, actively asking how a feature could be misused and who would be harmed; in the context of AI features, it is necessary to anticipate that a model can generate something unexpected or inaccurate (the example given is a recipe app where someone logged an allergy, and the model can suggest an ingredient that would cause a severe reaction), adding safeguards such as previews, confirmations and disclaimers, or even removing the feature when the safety risk outweighs the value.
- Familiarity: building on what people already know, using real-world metaphors (such as the trash can, which communicates discarding and allows recovery, the same way it does in the physical world) as long as they are neither too literal nor too abstract, at the risk of the metaphor not being understood or communicating the wrong thing (for example, using the trash icon for an action other than deleting breaks that familiarity). Familiarity also comes from consistency, both of behavior (visually identical elements should behave the same way) and of positioning (such as always closing a window in the upper left corner on the Mac), because that lets people anticipate what will happen and where to find things without having to think about it.
- Flexibility: recognizing that people use a design in contexts as varied as they are, adapting the experience to those contexts (the example given is listening to music at home through speakers, running with AirPods and Watch, or driving completely hands free); each device deserves a solution that makes the most of what makes it unique, with quick touch interactions on iPhone and deep flows with precise pointer control on Mac. Flexibility also means catering to people's wide range of abilities (age, languages, experience level, use of accessibility features), and, when there is no single solution that pleases everyone, allowing personalization (such as rearranging or hiding controls).
- Simplicity: does not mean minimalism; hiding all the functionality in a single place can make the interface look more minimalist without actually making it simpler. Simple designs are frictionless and intuitive, achieved by being concise (plain language, no jargon, no redundancy, fewer steps to complete tasks) and clear (hierarchy built with order, spacing and contrast, so that the most important item on the screen is always the most obvious); sometimes, simplicity means adding information and context instead of removing it, when that helps the person make an informed decision (the example given is a video play/pause control that gains additional context about the remaining time when resumed after a pause).
- Craft (craftsmanship, care): the attention to detail that shows care for the experience delivered, made of high quality materials, typography that is beautiful and legible on any device, colors that adapt well between light and dark, clear graphics and iconography, responsive animations with immediate and natural feedback, all on a foundation of reliable and secure SDKs; craft takes time, comes from constant iteration, and includes maintaining and evolving the design over time as new features and new hardware emerge.
- Delight: does not come from adding confetti or flourishes at the end of the process, but from deliberately identifying the emotion you want the person to feel (relaxed, confident, excited) and reinforcing it throughout the design; it is described as the natural sum of all the other principles executed well together.

Examples cited: the session is mostly conceptual, without naming specific real apps; the only detailed example scenario is hypothetical, a recipe app where someone logged an allergy and an AI feature can mistakenly suggest a dangerous ingredient, used to illustrate the responsibility principle.

Quotes:
"For us at Apple, design is making something with intention."
"Delight is the sum of the consideration you put into your product."

## Communicate your brand identity on iOS (id: wwdc2026_251, 17.4 min)

Basis: transcript and 13 of 13 frame sheets viewed, codes checked. Source: https://developer.apple.com/videos/play/wwdc2026/251/.

Central thesis: expressing brand identity in an iOS app does not mean replicating the brand identically across all platforms; it means, mainly, concentrating brand expression in the app's content layer (based on the two-layer model brought by Liquid Glass), preserving the native components and navigation patterns that people already expect from the system.

The design process Apple describes: thinking of the app as two distinct layers, the UI layer (global navigation and actions, such as tab bars and top toolbars, floating over the content) and the content layer (everything that makes up the features and the specific content of that app, right below the controls). The UI layer is the best place to lean on already familiar iOS patterns; the content layer is the best place to express brand identity. In practice, this becomes an audit exercise: identifying where standard system components (functional ones, like context menus) already solve the need well, and reserving customization effort for the areas of greatest impact on content. From there, the session goes through, with examples, four brand expression tools within this framing: UI components, use of color, typography and iconography (including logos).

Principles stated: leaning on already familiar iOS patterns for conventional tasks keeps people from having to relearn how to use the app; customized components require continuous refinement, so time should be invested in the areas of greatest impact, not in recreating utility components that already work well in the system standard (recreating something like a context menu from scratch tends to leave the app looking less native, or even dated, by replicating something already tested in an inferior way); color should be used to create meaning (hierarchy, grouping, indication of interaction), with restraint, since excess can overload the interface; typography should always be functional before expressive, which in practice means supporting Dynamic Type even with customized fonts; icons should be identifiable and serve a clear purpose, without needing to be highly detailed, and should respect platform conventions even when stylized (for example, the share icon should remain recognizable as such on iOS, Android and Web, even with its own strokes); on a device as personal as the iPhone, not supporting Dark Mode is treated as a negative experience that reflects on the product.

Concrete interface-building techniques:
- Before iOS 26, it was common for apps to use solid, colored backgrounds in top toolbars and tab bars, which thickened these UI elements and "letterboxed" the content area, reducing the available space; the recommendation now is to move the color into the content area (the scroll view), letting the Liquid Glass controls float above and pick up the brand color dynamically from what is underneath.
- Color concentrated in the so-called accent/tint color of actions and controls: primary actions, sections with new information, unread message badges, new message creation and the selected state in a tab bar.
- Context menus as an example of a flexible, often underestimated standard component: normally accessed by a button in the top toolbar, they bring together actions related to the entire screen (different from inline actions), support icons, grouping into sections with optional headers, and can open a submenu or a modal; in SwiftUI, this animation and behavior come ready-made.
- SwiftUI Zoom Transitions connecting the touch target to the transition state, used to give a sense of fluidity when opening related content (such as comments on a recipe).
- Dynamic Type: when using customized fonts, support must be tested and implemented manually (unlike system fonts, which already come with this support), ensuring that labels wrap across multiple lines instead of truncating when the font size increases; the same applies to the sizing of tabs and icons at larger accessibility sizes.
- System typeface family, San Francisco, with variants cited: SF Pro (default), SF Compact (optimized for small sizes), SF Mono (column alignment, geared toward code) and New York (serifed, for traditional reading and graphic/display use); SF Rounded is cited as one of the variants used to create variety and hierarchy even when using only system fonts.
- SF Symbols: more than 7,000 free symbols, built as a font (they scale dynamically like text), with multiple line weights and support for accessibility and localization, integrated directly into Xcode, with no need to export and manage separate icon libraries.
- Logos take up space that, in the context of iOS, is no longer necessary to remind the person which app they are using; the recommendation is discreet, non-intrusive use, without taking space from more relevant information.

Examples cited: Gentler Streak (fitness app with playful illustrations and detailed data visualizations in the content layer, but fully native tab bar and top toolbar navigation; spring-type animations in the monthly summary to highlight hierarchy; refined color palette also in dark mode; extensive use of system fonts, including the SF Rounded variant, to achieve variety without leaving the standard); Slack (customized top toolbar, with a central action showing channel information, but keeping button sizes, floating action positioning and popover behavior in the iOS standard; color used sparingly, in primary actions, badges and the selected state of the tab bar; background color moved to the content area, letting it scroll out of view and the content occupy the screen edge to edge); Moonlitt (moon phase app with flat hierarchy, no tab bar; a customized lunar cycle calendar component that still uses iOS visual language, with a Liquid Glass background, a primary dismiss action and concentric edges with the hardware; edge-to-edge content mimicking the gradation of the night sky; a context menu used for settings, with the standard morphing animation from the tapped action); Crumbl (full-bleed videos that change weekly to highlight the flavors of the week; its own typography, Crumbl Sans, used in large, bold headers, especially in the flavor names; widget with the brand's own pastel color palette, cited as immediately recognizable); NYT Cooking (SwiftUI Zoom Transitions used in viewing comments on a recipe; its own icons with sharper strokes and a thin line-weight variant, used consistently in tab bar, top toolbars and inline actions; explicit comparison between the three versions of the share icon on iOS, Android and Web, all faithful to their own platform's convention despite the distinct style; logo appearing only in the Home tab and disappearing on scroll, as an example of discreet branding).

Quotes:
"People remember how a product makes them feel."
"Don't be afraid to use color in your app!"

## Icon Composer for Beginners Group Lab (id: wwdc2026_8012, 61.7 min)

Basis: transcript and 43 of 43 frame sheets viewed, codes checked. Local automatic transcription done with Whisper, not Apple's official one; proper names and terms may have mishearing errors. Source: https://developer.apple.com/videos/play/wwdc2026/8012/.

Central thesis: In a group question-and-answer lab led by Mike Stern (head of the Design Evangelism team), Apple designers and engineers argue that the app icon should be born from a simple idea, drawn with simple, elegant vector shapes, and that Icon Composer exists to transform that single, resolution-independent expression into an icon that adapts on its own to sizes, platforms, appearance modes and the system's own Liquid Glass material. The author's role is to provide a clean layered construction and well-thought-out annotations; the system takes on the adaptation and rendering, and the author refines whatever is needed by testing at real size.

The design process Apple describes:
Demonstration of Icon Composer (Liam, with the Photos app icon):
1. Drag layers coming from other design tools into the left column and organize them on the z axis, in groups and layers.
2. Configure the background on the canvas: solid color or gradient, or automatic mode, which uses system light in light mode and system dark in dark mode.
3. Select each layer and adjust appearance (color, opacity, blend modes, fill, including replacing the SVG) and composition (position, visibility), deciding whether it goes into Liquid Glass or not.
4. Select each group and adjust the glass properties: specular, blur, refraction, translucency and shadows.
5. Review the variations by platform (iOS, macOS, watchOS) and by mode (dark, mono, clear and tint), adjusting the color fills to optimize legibility.
6. Use the preview panel: solid or custom backgrounds, overlaid icon grid, size controls and comparison with OS26's backward-compatible rendering (term uncertain in the automatic transcription).

Workflow for drawing an icon from scratch (Lance, with additions from other participants):
1. Have an idea: a visual metaphor that represents what the app wants to communicate, which can also reference part of the app's interface.
2. Draw the icon in a design tool, thinking about the composition and about how the layers are drawn and organized.
3. Export the layers as individual files, at the full size of the canvas.
4. Drag the layers into Icon Composer, which works as a second stage: annotate the icon, control how color applies to each element for the appearance modes and control how Liquid Glass applies to each layer.

Verification on the device (answer about the most common mistakes):
1. Treat the icon like code: build, design and then test, without skipping the test.
2. Evaluate at all sizes and presentations, from smallest to largest, using the "waterfall" feature that, according to the speaker (with hesitation), Icon Composer has to show the common presentation sizes all at once, and alternating backgrounds.
3. Put the icon in a group on the home screen, where it is at the smallest possible size on the iPhone screen (guidance that the speech says predates Icon Composer).
4. Go outside with the iPhone, look at the icon with the arm moving under daylight and among dozens of other icons chosen at random, and ask whether it has presence and stands out.
5. Adjust color or shape to accentuate what makes the icon unique.

Updating an icon made for iOS 26 to the iOS 27 look (Lance and others):
1. Open last year's file in the updated Icon Composer and see the new rendering applied automatically, without touching annotations or artwork.
2. Review the specular highlights, especially with overlapping layers, check what the automatic setting does and switch to inside or outside according to the layers' colors.
3. Fine-tune the shadows and configure the refraction when there are overlapping layers.
4. Review the translucency manually, because the reduction Apple applied to its own icons does not happen automatically.

Integration in Xcode (John):
1. Drag the Icon Composer file into the project, alongside the Swift files, as a common resource.
2. Check the target association suggested by Xcode in the import dialog.
3. In the target editor, make sure the app icon name matches the file, usually "app Icon", without the "dot Icon" at the end.
4. Remove the old icon from the asset catalog, if it exists. There was no change to this process compared to the previous year.

Process for beginners with no design experience (several participants):
1. Define how to represent the app, how you want people to remember it and what essence to capture in a small space.
2. Close the computer and sketch by hand on paper with a pencil, without needing to be a good artist.
3. Spread out and stick up the sketches, look at them and ask friends what they feel, like the raw storyboards of Pixar movies.
4. Alternatively, write what the app does and what is unique about it, or talk to someone, record it and listen back looking for objects and metaphors used; sometimes the app's own name is the metaphor.
5. Only after settling what you want to communicate, move on to rendering and tools, asking how much can be simplified without losing the meaning.
6. Think about the layered construction and the composition.

Principles stated and why:
- Use simple, powerful vector shapes, simple and elegant geometries, and not fine, complex details. Why: the icon appears anywhere from a tiny rectangle in Settings or a Mac menu to a huge billboard, and complex detail is hard to adapt to that range of conditions; that is why some of the best logos in the world are the ones built with the most simplicity and still communicate with strength.
- Do not overdo complexity, especially with the new glass features. Why: these effects are delicate and powerful; refraction looks good because it scales well, and glass is very sensitive to the number of shapes, their size and how they overlap, so minimal movements on the refraction control change the result a great deal.
- Draw at the right size and export the layers at the full size of the canvas. Why: the layers arrive in Icon Composer already in the correct position, it saves time and avoids surprises on the device, where the icon needs to work small.
- Prefer scalable vectors (SVG) over bitmaps, although bitmaps are accepted. Why: moving from a raster world to a resolution-independent representation solves the problem of the icon that goes from tiny to huge, and the effects, composition and adaptation to the rendering modes are nearly impossible with a set of bitmaps delivered ready-made. For certain brand styles or app types, the bitmap is still the right choice.
- See the icon the way the customer will see it. Why: on a large Mac screen the icon appears much larger than its natural size.
- A living icon that adapts, instead of a static set of pixels. Why: the icon belongs to many people and audiences (whoever draws it, the engineering team or the product it is part of), it is visual and marketing identity and lives in an ecosystem; the user is also a stakeholder. Light mode, dark mode, clear adaptation and harmony with the system's design language are hard with static pixels, and a cart of bitmaps executed one by one does not evolve along with the system. The load is split: the author provides a simple, elegant expression, and Apple adapts and renders it with quality as the device's conditions change.
- Bring the interface's design language and material quality to icons fully, not superficially. Why: the material needs to work with each element, of different sizes and colors, and that requires giving the author precise control over the glass; since icons coexist in a shared space, a shared language makes the experience more harmonious.
- A single file for all platforms and modes. Why: before, it was necessary to make separate icons for watch, iOS and macOS and, with dark, clear and tint modes, imagine individual PNGs for each one, which sometimes did not work well in another context.
- Consistency between icons. Why: it makes it possible to guarantee, for example, the same dark background in dark mode across both Apple and third-party icons. One participant compares it to having a high-level API like SwiftUI instead of low-level system programming, from which more interesting things can emerge and adapt over time.
- Clear mode glass in icons does not respond to the system's Liquid Glass transparency control in iOS 27; it stays constant, by deliberate decision. Why: in the system's glass there is some notion of foreground and background content, but an icon can have anything, and it was necessary to guarantee a consistent, legible experience in every case; also, on iOS the icon deals mostly with different wallpapers, not with system glass underneath.
- Adapt the flat brand to the medium, as has always been done in graphic design. Why: a logo appears on a form, a business card, letterhead, a physical product, a car's logotype, motion in an ad, and in each medium the identity is executed in the most natural way so that it keeps coming through; the icon, as the app's face, is sometimes wearing sunglasses and a hat and remains recognizable as long as it connects clearly to the brand's other representations.
- Do not rely on color to convey meaning. Why: people with color blindness, such as red-green color blindness, may not perceive the color; the recognizable shape, with highlights, shading and real contrast, also needs to work in clear and tint modes. A good "shape algebra" or shape design language comes before colors, gradients and glass effects, so that the icon is immediately recognizable to everyone, which is presented as brand design rule number one.
- Maximize the dynamic range in mono mode annotations. Why: very dark darks and very light lights are transformed according to the color the user picks for icons from the wallpaper, and that sustains the contrast.
- Keep at least part of the foreground element white or nearly white. Why: some tint colors chosen by the user are naturally light in luminance, such as yellow, and that helps guarantee contrast; Apple does this in its own files.
- Prefer the backgrounds provided by the system and watch the luminance of your own gradients, especially in mono mode. Why: system backgrounds give maximum contrast and are already optimized for the new glass rendering.
- Keep a single visual identity across all system versions, without giving up the icon's fundamental shape. Why: the brand's current visual identity is the most important thing, and Apple delivers the icon with full quality and the correct corner radius also in old presentations, such as "I was 17" (term uncertain in the automatic transcription) and earlier ones, and on the product page on the App Store.
- Let the container shape guide the composition by platform. Why: the watchOS circle does not have the same layout or asymmetry possibilities as the rounded rectangle, and a circle sits well centered inside another circle.
- Simplify without losing the meaning. Why: not everything fits at small size; a piano app does not need all 88 keys in the icon, but one key might be too few.
- Good automatic defaults. Why: the automatic specular highlight should work without the author needing to touch it, by taking into account the color of the layer and the background and choosing inside or outside on its own.

Concrete interface-building techniques, with exact numbers when stated:
- Canvas background: solid or gradient; automatic mode with system light in light mode and system dark in dark mode, backgrounds already optimized for the glass. New: automatic gradients, where you set the brand color and the app generates a background gradient.
- Layers and groups: Liquid Glass properties apply at the group level; separate layers into distinct groups to configure them independently. Imported layers become glass by default; it's possible to turn this off so they stay as flat graphics, useful for raster art that's already pre-rendered (cases like Camera and Preview) or something like a watermark, which wouldn't make sense to be glassy.
- Specular: light drawn around the edge of the object that gives definition. This year it's sharper and contains dark parts that help define the shape. Automatic by default; inside draws inside the shape and works well when the foreground is darker than the background; outside works better when the background is darker than the foreground.
- Blur: blurs the layers and gives the sensation of frosted, refractive glass.
- Refraction: two-dimensional control; the vertical axis controls the height of the refraction (the radius gets rounder as it goes up) and the horizontal axis controls the intensity, bringing more of the artwork into the shape. There's an inverse refraction, which wraps the edges in the opposite direction. The 2D control accepts modifier keys to lock one of the values. For the Photos icon, the result that worked both large and small landed in the middle of the range.
- Translucency: more transparent at the bottom and retaining color at the top, compared to the new Siri glass. This year Apple reduced translucency in many of its own icons so they'd be sharper and more legible, an adjustment that depends on the color and size of the layer; it's still used, for example, in the Podcasts icon to show the refraction between layers.
- Shadows: now they're "ring shadows," with more definition at the edges, reinforcing the material. Chromatic shadows pick up the color of the layers that bleeds into the background; neutral shadows are desaturated versions. Shadows also help show that one element passes underneath another.
- Blend modes, as described in the talk: normal replaces the pixel below without its contribution. The upper group is called additive and darkens: darken, multiply and plus darker (said as "plus L, or plus D"; term uncertain in the automatic transcription), which keeps the vividness of the color below and helps sell the glass, but does little against a dark background. The next group is called subtractive and lightens the object relative to the background: lighten, screen and plus lighter (said as "plus L"; term uncertain in the automatic transcription), which is like a screen that keeps the vividness, while screen becomes more desaturated. The modes give more color intensity and control over how the glass layers blend, since imported layers arrive opaque. Numeric example stated: red 255, 0, 0 and green 0, 255, 0 combined with screen would give 255, except in HDR. Red glass overlaid on yellow glass in the real world would tend toward a darker amber orange, something close to what multiply or plus darker, perhaps with an opacity adjustment, can help achieve. Plus lighter and plus darker are used extensively in the glass of system controls, with very similar math.
- Mono mode: a single grayscale annotation covers light clear, dark clear and all tint modes; the annotations need to meet contrast requirements.
- Tint mode: the tint color is exposed in Icon Composer, from desaturated to vivid; optimize for light colors like yellow while keeping the foreground white or nearly white.
- Complex shapes in tint mode: detail that's too fine or too many elements around it also hurt the contrast.
- Interlaced overlap (the Apple Developer app icon, where the pencil, brush and ruler pass over one another in a cycle): slice the elements into several individual layers and reassemble them so one shape appears to pass behind another, using shadows; seen from the side, the construction tells a different story than seen from above. Compared to an icon in the "MCS Hesher-esque" style (term uncertain in the automatic transcription).
- From flat brand to glass: expose layers that in the logo were rubber paths or subtractions; for example, eyes on top of a face instead of cut out of it. In the Podcasts icon, rubber paths became solid shapes to look like stacking. Simple shapes call for different properties than typographic marks, thin strokes or details.
- Templates for four applications: Figma, Sketch, Illustrator and Photoshop; the Illustrator one has a recommended script to position the vectors and keep the position relative to the canvas. Export as SVG or PNG. The design resources include a sample file with layers to compare last year's rendering with this year's.
- Preview: solid background or your own image to see refraction on the "chiclet" and contrast, an overlaid icon grid, size controls and comparison with the backward-compatible rendering.
- Composition by platform: move and scale elements in the composition panel; in Maps, the asymmetric layout of the rounded rectangle becomes, on the watch, the position marker centered in the circle.
- Legacy icons: without an Icon Composer file, the system automatically segments old icons into basic documents and renders them; in iOS 27 the foreground elements become more prominent and less translucent than in iOS 26, and for anyone who prefers the earlier, more translucent look, the talk says it's time to create the version in Icon Composer, which gives full control over the appearance.
- An iOS 26 icon made in Icon Composer adopts the iOS 27 look automatically, without recompiling the app.
- Getting it: it comes with Xcode or as a direct, standalone download; the Icon Composer site, cited from memory as "developer.apple.com slash Icon Composer," with a caveat from the speaker, has a download link, a mini tour and a comparison of the Photos icon in iOS 26, unadjusted in iOS 27, and optimized.
- Device Hub (also said as "Device's app"; term uncertain in the automatic transcription): simulates the appearance of icons in light, dark and appearance variants without compiling on the device, also useful for Watch.
- Usability improvements since the version released with iOS and macOS 26: selection annotations in the interface, snapping to guides and grids, copying and pasting attributes from one icon to another. A participant comments, without explanation, that they expected to hear "HDR HeekX" (term uncertain in the automatic transcription).

Examples cited:

## What this group reveals about the Apple way

A process with named phases appears as a recurring pattern across very different domains: pre-production/production/post-production for immersive environments (id 234), explore/bring in real content/tune interactions for prototyping with agents (id 227), and UI layer/content layer as a conceptual structure for branding (id 251). Apple always seems to prefer naming and sequencing explicit steps of a process, rather than describing an outcome with no path to it.

Testing early and on the real device, not just on the computer screen, is consistently valued across technical sessions that are very different from each other: Reality Composer Pro 3 praises iterating directly on Vision Pro (id 252), the session on prototyping with agents in Xcode recommends Previews and tuning panels side by side to shorten the feedback loop (id 227), and the session on graphical SwiftUI mentions the sample app with a navigable preview to play with the shader's parameters (id 322).

Naming and writing well (naming, voice, tone) is treated as a first-class design decision, not as a copywriting task fitted in afterward: there is an entire session dedicated to naming criteria and exercises (id 290), and the video on general principles also explicitly states that the words used affect how people feel (id 250), just as the branding session treats voice and tone as a deliberate part of identity (id 251).

Deliberate restraint appears as a recurring value, not as a technical limitation: simplicity is not minimalism, but rather the absence of friction with clear hierarchy (id 250); color must be used sparingly and with purpose, never as decoration (id 251); custom iconography does not need to be very detailed to work (id 251); and UI customization should concentrate only where it has the greatest impact, leaving the rest at the platform default (id 251, id 227).

New APIs, both in SwiftUI and on the web, tend to compose semantic blocks that already exist rather than replacing them with something proprietary: the native HTML select gains full customization without losing built-in accessibility (id 315), CSS Grid Lanes reuses syntax already known from Grid (fr, gap, span, subgrid) to solve a problem previously only solved with JavaScript (id 314), and the new document API in SwiftUI is described as an expansion on protocols that already existed (id 269). The advanced graphical effect from id 322 sums up this spirit explicitly, the advanced part is in how the simple pieces connect, not in new complexity.

AI tools and agents are consistently positioned as collaborators under human supervision, never as autonomous decision-makers: the session on prototyping with agents is explicit about this (id 227), and the session on general principles treats responsibility for AI-generated suggestions (including potentially dangerous ones) as the responsibility of whoever designs the product, not of the model (id 250).
